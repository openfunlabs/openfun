# OpenFun 质量提升实施方案

状态：分阶段实施。本文定义产品改造和验收，不代表生成质量已经达标。评测使用 [evaluation-v1.2](evaluation.md)，历史结果保持原版本。首批交付是本方案、评测规范和评测记录校验工具；下表其余能力须分别实现、验证后再标记完成。

## 目标与约束

普通用户的一段需求应得到美术统一、动作清楚、玩法成立、能持续发展的可玩作品。提升对象是 OpenFun 的生成能力，而非人工修好某一个样例。所有改进需在新项目中重新生成验证，同时保留首版和后续 polish 的独立结果。

优先修复最弱的适用质量维度，不以素材数量、系统数量、提示词长度或工具调用次数衡量进步。复用项目已有工具、资源和引擎原生能力。运行时继续使用受 schema 约束的数据、已实现行为和已导入资产；动态执行任意生成代码不属于本轮。

新游戏仍须生成并查看视觉目标、生成并应用无文字 UI 皮肤。生产美术不得被程序绘制的占位物静默替代；已有授权资源与用户明确例外按原规则处理。资产来源、许可证和必要声明必须保留。服务失败应标记未完成，不伪造成功。不得为了降低成本削弱这些要求。

## 当前基础与实际缺口

| 领域       | 已有基础                                     | 本轮需要补齐                                             |
| ---------- | -------------------------------------------- | -------------------------------------------------------- |
| 资产       | 搜索、图片/模型生成、导入及来源记录          | 面向引擎的资源契约、稳定加工、动作与材质验收             |
| 玩法与动画 | 设计指南、Godot 预览、动画及死亡辅助工具     | 从输入到状态变化再到画面反馈的可重复证据                 |
| 检查       | 源码清单、引擎导入检查、截图与帧时间         | 区分静态合规、真实运行与主观质量；防止过期证据复用       |
| Polish     | 隔离候选、回滚、最终修改后预览、导入检查     | 结构化缺陷、前后对照和受影响行为回归；自评不能当独立验收 |
| 运行时     | 有界队列、去重、预算、取消、持久化及状态修订 | 各类型内容的语义验证、实际激活/游玩证据、阶段耗时        |
| 评测       | A–E 案例、门槛、分维度评分、独立试玩要求     | 可校验的证据记录、负向控制、改动后的回归矩阵             |

`world_review_game` 的源码清单不能认证画质；`world_check_game` 的导入成功不能证明有趣；预览默认不产生新 AI 内容，不能替代真实运行时续写测试。

### P0：证据先于结论

每份评测记录包含项目快照摘要、阶段、评审者、完成状态、G1–G7 和 Q1–Q10。每条证据包含文件摘要、采集时间、场景、输入/观察方式、观测结果以及对应快照。评分必须引用证据并说明局限；未知维度为 NV，不能默认为成功。

本批校验器只验证记录结构、引用和磁盘文件一致性。文件真实存在不代表内容真实，也不代表证据足够支撑评分。独立试玩负责判断证据内容和评分，人类负责确认主观趣味。校验器不启动模型或判定产品发布。它不读取历史 v1.1 为 v1.2，也不改写任何评测结果。

### P1：把资产转成可用资源

先实现 2D 资源清单：稳定 ID、源文件摘要、来源/许可路径、尺寸、方向、裁剪矩形、透明边界、轴心、逻辑占地与显示缩放、动作名称、每帧时长、循环方式、事件时刻。资源名称与游戏语义关联，玩法引用稳定 ID，替换图片不修改行为逻辑。

加工过程可重跑：同一输入和配置得到相同资源；保留原件，拒绝越界裁剪、空帧、无效时长和缺失动作。先输出 Godot 原生资源，再在引擎中加载和播放。检查器分为文件/元数据、引擎加载、运行中表现三层，不能仅看 JSON 合法。风格一致性、剪影、景深、光照与主体可读性仍要看实际画面。

3D 阶段扩展材质槽、比例、朝向、骨架、动作映射与 root motion 策略；保留源材质，不为消除报错静默替换。可复用动画应优先复用，动作导出只含所需片段。缓存键包含源摘要、加工配置和工具版本，避免重复付费或误用旧产物。

### P2：先做完整的短段游玩，再扩展内容

生成流程先明确玩家目标、可用动作、状态转换、成功/失败和恢复路径。首个可玩段落须验证一次有意义的选择及其后果，然后才扩大场景和内容。组件复用限于输入、交互、存档、动作播放等小能力，不用整套模板替代需求理解。

动作检查覆盖准备、有效动作、接触/落空、恢复、打断、死亡和清理；伤害与接触时刻一致，死亡后失去攻击能力但不瞬间消失。按类型评估，不给非战斗游戏强加攻击。可读反馈结合人物、目标、声音、UI；镜头抖动和粒子不能代替动作本身。

增加带种子/初始状态的输入轨迹与状态断言，记录实际画面和引擎状态。每个断言写明可证明范围：到达目标只证明该路线可达，不证明所有关卡都可解。UI 覆盖长文本、焦点、禁用/等待、失败重试、不同分辨率；音频检查循环接缝、状态切换、混音和静音。

### P3：生成的是选择与后果

分别为动作探索、解谜、调查和经营建立内容契约：前置条件、可用行为、资源消耗、后果、奖励和延续关系。通用 schema 验证之外，按类型验证连通性、资源守恒/可负担性、线索前置依赖、互斥条件和完成路径。只对明确建模的状态空间宣称可解或可达。

内容必须经请求、生成、校验、发布、激活、实际游玩和保存重访的完整链路。每一步关联 job/content ID 与状态修订；发布不能算游玩。无效内容不激活、不覆盖有效存档，保留诊断并允许受预算约束的恢复。续写丰富度按新情境中的决策变化评估，换名字、调数值和加数量不能单独算质量提升。

### P4：改进必须有前后对照

每轮记录具体问题、预期改善、前后证据、受影响功能和回归结果；保留现有一次一到两个主要问题的范围。优先改善最弱环节，不反复只优化开场截图。变更后证据必须绑定新快照，不能用修改前预览支撑接受。

控制器继续验证原项目未变、候选导入通过、结果来自真实工具完成事件，失败回滚。结构化记录是必要条件，不是充分条件；不能将模型自评升级为独立质量分。无收益、能力阻塞、需改变存档契约时停止并说明，不引入固定 polish 轮数上限。

### P5：降低浪费，同时保持质量

按排队、provider、下载、加工、引擎导入、校验和激活拆分耗时，记录冷启动与重用。等待时提供可理解状态，并尽量允许继续玩已完成内容。基于玩家方向和进度预取，保留有界队列、去重、取消和预算预留；不能扩大并发掩盖浪费。

付费操作复用已保存任务 ID；请求结果不确定时先查询状态，禁止自动重复提交。记录实际 tokens/credits/服务账单，未知金额保持未知。分别测首个可玩时间、完整交付时间、后续内容等待、尾部帧时间与失败恢复；不得用平均 FPS 或廉价但未达标的结果宣称优化成功。

## 开发与验收顺序

1. 对每个阶段先建立能失败的检查：错误轴心/动作片段、不可达目标、假胜利、无效状态、过期截图等负向样例属于工程测试，不作为生成成功案例。
2. 完成最小纵向能力，运行聚焦测试、类型/格式检查与构建。涉及实际游戏呈现时再运行引擎和真实渲染验证。
3. 使用普通需求在空项目生成，冻结首版；按评测规范独立试玩并记录问题。开发中的单项检查不授予完整产品通过。
4. 修改产品后重新生成同类需求和其他类型/未暴露需求，比较全部尝试。冻结候选后才执行每个核心案例至少三次的验收，不挑最好样本。
5. 每阶段独立提交范围和回滚边界；状态/资产格式新增版本时先定义兼容性。现有世界与存档不应被实验自动迁移。

## 完成标准与风险

代码通过测试只能证明对应工程检查成立。产品质量完成必须满足评测门槛、各适用维度至少 3、真实续写与持久化证据，以及单独记录的真人试玩。当前尚无本方案实施后的产品质量结论。

主要风险是工具能运行但输出仍然不好、验证器漏检、模型针对已知样例优化，以及画质提升带来加载/激活卡顿。分别用实际游玩、负向控制、未暴露需求和分阶段性能采样处理。任何阶段发现质量回退，保留失败证据、回滚该阶段，不降低验收线。
