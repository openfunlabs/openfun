# OpenFun 质量提升实施方案

本次一次性完成评测、资产加工、动画与玩法、持续内容、Polish、延迟和成本控制的全部改造，统一验收后交付。文档和评测记录校验工具已有实现，其余改造及产品质量验证仍待完成。仅完成其中一项不算本次交付完成。

评测使用 [evaluation-v1.2](evaluation.md)，历史结果保留原版本。

## 目标与约束

用户提出需求后，OpenFun 应能生成美术统一、动作清楚、选择有意义、后续内容值得继续玩的游戏。每次改进都要在新项目中重新生成验证，首版和后续 polish 分开评测。人工修好一个样例不足以证明生成能力提高。

优先修复评测中最弱的适用维度。增加素材、系统、提示词或工具调用次数，本身不算进步。实现时优先复用已有工具、资源和引擎原生能力。运行时继续使用受 schema 约束的数据、已实现行为和已导入资产；本轮不开放任意生成代码的动态执行。

新游戏仍须生成并查看视觉目标，生成并应用无文字 UI 皮肤。未经用户明确许可，不能用程序绘制的占位物替代成品美术。已有授权资源的复用按原规则处理，资产来源、许可证和必要声明必须保留。服务失败就标记未完成；降低成本不能成为跳过这些要求的理由。

## 已有能力与缺口

| 领域       | 已有基础                                     | 本轮需要补齐                                             |
| ---------- | -------------------------------------------- | -------------------------------------------------------- |
| 资产       | 搜索、图片/模型生成、导入及来源记录          | 面向引擎的资源契约、稳定加工、动作与材质验收             |
| 玩法与动画 | 设计指南、Godot 预览、动画及死亡辅助工具     | 从输入到状态变化再到画面反馈的可重复证据                 |
| 检查       | 源码清单、引擎导入检查、截图与帧时间         | 区分静态合规、真实运行与主观质量；防止过期证据复用       |
| Polish     | 隔离候选、回滚、最终修改后预览、导入检查     | 结构化缺陷、前后对照和受影响行为回归；自评不能当独立验收 |
| 运行时     | 有界队列、去重、预算、取消、持久化及状态修订 | 各类型内容的语义验证、实际激活/游玩证据、阶段耗时        |
| 评测       | A–E 案例、门槛、分维度评分、独立试玩要求     | 可校验的证据记录、负向控制、改动后的回归矩阵             |

`world_review_game` 列出源码和资源清单，标出候选问题；`world_check_game` 检查引擎导入。画质和趣味仍需试玩判断。预览默认不产生新 AI 内容，续写必须通过真实运行时测试。

## 一次性交付范围

下列模块全部纳入同一次交付。开发按依赖推进，模块检查通过后继续完成其余改造，最终对同一候选版本统一验收。

| 模块       | 实施位置                                | 必须完成的改造                                              | 验收要求                                                   |
| ---------- | --------------------------------------- | ----------------------------------------------------------- | ---------------------------------------------------------- |
| 评测基础   | `tests/evaluation/`、评测规范           | 结构化记录、文件摘要校验、版本与评测环节绑定、失败记录保留  | 拒绝缺失、篡改、越界证据及重复评分；记录有效不等于质量通过 |
| 资产加工   | `src/assets/`、`src/godot/`、Godot 工具 | 2D 和 3D 资源清单、可重复加工、原文件保留、原生资源加载检查 | 检查器能发现错误资源；资源在引擎中加载并正确播放           |
| 动作与玩法 | 动画工具、预览、玩法指南                | 输入时间线、状态断言、动作表现及行为回归                    | 验证命中、落空、打断、死亡，以及目标推进、失败和重试       |
| 持续内容   | `src/generation/`、运行时协议及设计指南 | 可组合内容契约、分类型语义验证、激活记录                    | 后续内容改变玩家决策，保存重访不丢失状态或身份             |
| Polish     | `src/polish/`                           | 问题、假设、修改、前后对照和回归记录                        | 拒绝验证失败或证据过期的候选；保留隔离与回滚               |
| 延迟与成本 | Host、生成队列、资产服务调用            | 各环节耗时、复用和重复提交统计、有界预取                    | 在同等质量下比较；慢服务、取消和重试不破坏状态及预算       |
| 产品评测   | 安装包与真实服务评测                    | A/B 校准、C–E 与未暴露需求、冻结候选验收                    | 全部适用维度至少 3、全部适用门槛通过，真人反馈单列         |

开发依赖：评测基础为所有模块记录证据；资产加工支撑动作与玩法验证；玩法和状态规则支撑持续内容验证；Polish 使用修改前后的证据和回归检查；延迟与成本测量覆盖资产与内容生成全过程。所有模块接通后，再冻结完整候选版本做产品验收。2D 与 3D 均须在本次完成。

### 记录评测证据

每份评测记录包含项目快照摘要、阶段、评审者、完成状态、G1–G7 和 Q1–Q10。每条证据包含文件摘要、采集时间、场景、输入/观察方式、观测结果以及对应快照。评分必须引用证据并说明局限；未知维度为 NV，不能默认为成功。

评测记录校验器检查记录结构、引用和文件摘要。评审者仍需独立试玩，核实证据是否支持评分；趣味需要真人反馈。校验器不调用模型、不判定能否发布，也不改写评测结果。v1.1 记录不会自动转为 v1.2。

### 把资产转成可用资源

先实现 2D 资源清单：稳定 ID、源文件摘要、来源/许可路径、尺寸、方向、裁剪矩形、透明边界、轴心、逻辑占地与显示缩放、动作名称、每帧时长、循环方式、事件时刻。资源名称与游戏语义关联，玩法引用稳定 ID，替换图片不修改行为逻辑。

加工过程须可重复：同一输入和配置得到相同资源。保留原件，拒绝越界裁剪、空帧、无效时长和缺失动作。输出 Godot 原生资源后，在引擎中加载和播放。检查覆盖文件与元数据、引擎加载、运行表现三层；风格、剪影、景深、光照和主体可读性要看实际画面。

3D 资源清单还须包含材质槽、比例、朝向、骨架、动作映射与 root motion 策略；保留源材质，不为消除报错静默替换。可复用动画应优先复用，动作导出只含所需片段。缓存键包含源摘要、加工配置和工具版本，避免重复付费或误用旧产物。

### 先做完整的短段游玩，再扩展内容

生成时先明确玩家目标、可用动作、状态转换、成功与失败条件，以及失败后如何继续。首段游玩须包含一次有意义的选择和可见后果，验证后再扩展场景与内容。复用输入、交互、存档、动作播放等组件；游戏设计仍须回应用户需求，不能直接套用整套模板。

动作检查覆盖准备、有效动作、接触或落空、恢复、打断、死亡和清理。伤害应在接触时发生，角色死亡后失去攻击能力，并完成死亡表现再清理。非战斗游戏按实际交互评估。人物动作、目标反应、声音和 UI 要让玩家看懂结果；镜头抖动和粒子不能代替动作本身。

增加带种子/初始状态的输入轨迹与状态断言，记录实际画面和引擎状态。每个断言写明可证明范围：到达目标只证明该路线可达，不证明所有关卡都可解。UI 覆盖长文本、焦点、禁用/等待、失败重试、不同分辨率；音频检查循环接缝、状态切换、混音和静音。

### 让后续内容改变玩家的选择

分别为动作探索、解谜、调查和经营建立内容契约：前置条件、可用行为、资源消耗、后果、奖励和延续关系。通用 schema 验证之外，按类型验证连通性、资源守恒/可负担性、线索前置依赖、互斥条件和完成路径。只对明确建模的状态空间宣称可解或可达。

跟踪内容从请求、生成、校验、发布、激活到实际游玩、保存重访的全过程，每一步关联 job/content ID 和状态修订。只有玩家实际进入并体验过的内容才计入游玩样本。无效内容不得激活或覆盖有效存档，须保留诊断，并在预算内支持恢复。评测时说明新情境如何改变玩家的决策；换名字、调数值和加数量不能单独算质量提升。

### 改进必须有前后对照

每轮围绕一到两个主要问题，记录预期改善、前后证据、受影响功能和回归结果。优先修复最弱环节，检查范围要覆盖后续游玩。修改后重新采集证据并绑定新快照，不能拿旧预览证明新版本有效。

控制器继续检查原项目是否被改动、候选是否通过导入检查、结果是否来自真实工具完成事件，失败就回滚。模型自评须与独立质量评分分开。没有改善、工具能力不足或需要改变存档契约时，停止并说明原因。仍不设置固定 polish 轮数上限。

### 测量延迟，减少重复工作

分别记录排队、provider、下载、加工、引擎导入、校验和激活耗时，区分冷启动与资源复用。等待时显示当前进度，尽量让玩家继续玩已完成的内容。根据玩家方向和进度预取，保留队列上限、去重、取消和预算预留，避免并发请求中混入重复工作。

付费操作复用已保存任务 ID；请求结果不确定时先查询状态，禁止自动重复提交。记录实际 tokens/credits/服务账单，未知金额保持未知。分别测首个可玩时间、完整交付时间、后续内容等待、尾部帧时间与失败恢复；不得用平均 FPS 或廉价但未达标的结果宣称优化成功。

## 开发顺序与统一验收

1. 先用已知错误验证检查器：错误轴心或动作片段、不可达目标、假胜利、无效状态、过期截图等。此类样例只用于工程测试，不计入生成成功案例。
2. 先做通一个最小使用流程，运行相关测试、类型和格式检查及构建。涉及游戏呈现时，还须运行引擎并检查实际渲染结果。
3. 使用普通需求在空项目生成，冻结首版；按评测规范独立试玩并记录问题。开发中的单项检查不授予完整产品通过。
4. 修改产品后重新生成同类需求和其他类型/未暴露需求，比较全部尝试。冻结候选后才执行每个核心案例至少三次的验收，不挑最好样本。
5. 所有模块完成后，对同一候选版本统一验收并交付。记录各项改动和回滚方式；状态或资产格式升级前先定义兼容性。实验不得自动迁移现有世界与存档。

## 完成标准与风险

产品验收要求各适用维度至少 3、全部适用门槛通过，并提供真实续写、持久化和单独记录的真人试玩证据。工程测试通过后，仍须完成这些评测。当前尚无本方案实施后的产品质量结论。

主要风险是工具能运行但输出仍然不好、验证器漏检、模型针对已知样例优化，以及画质提升带来加载/激活卡顿。分别用实际游玩、负向控制、未暴露需求和各环节性能采样处理。发现质量回退时，保留失败证据，修复或回滚引入问题的改动，再对完整候选版本重新验收，不降低验收线。
