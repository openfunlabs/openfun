# Animation and physical feedback

Use for attacks, movement, interaction and enemy reactions. Pick techniques appropriate to 2D sprites, cutout animation, 3D rigs or deliberately stylized motion. More particles are not a substitute for an action.

## Build a readable action

For melee, make the visible weapon travel with the hand/body through anticipation, contact and recovery. Share the attack state and timing with damage detection. An effect-only white ring cannot stand in for a sword swing. Attach the weapon to a pivot/bone; choose authored AnimationPlayer tracks, sprite frames or skeletal clips according to the art. In 3D, check the grip, body weight shift and feet as well as the blade.

GDQuest demonstrates a weapon sprite and hit area moving together, with the collision shape enabled during the attack. Its animation example explains anticipation, trails and easing. These are useful starting points, not a required art style. [Hitboxes and hurtboxes](https://www.gdquest.com/library/hitbox_hurtbox_godot4/), [Juicing attacks](https://www.gdquest.com/library/juicy_attack/).

Implement one authoritative attack instance with an active window and a set of already-hit target IDs. Detect contact only while active; do not damage every frame of overlap unless repeated ticks are explicitly designed. Use physics-tick overlap or swept shape tests for fast motion, not merely distance from the actor. Keep walls, team filtering, multiple hurtboxes and invulnerability consistent. Clear attack state on interruption, death and scene exit. A trail enhances an already visible weapon; hit sparks belong at contact, not the actor's center.

Give the receiver an appropriate reaction: pose change, interruption, recoil, sound, or deliberate armor feedback. Communicate a miss differently from a blocked or successful hit. Optional short hit-stop and restrained camera impulse must preserve input and readable enemy tells; offer reduced shake/flashes. Don't globally freeze HTTP, UI or save recovery to create impact. Feedback amplifies action, as illustrated by [Juice It or Lose It](https://gdcvault.com/play/1016789/Juice-It-or-Lose).

## Defeat is a state transition, not immediate removal

On the first lethal hit, commit a stable death ID and reward/quest consequences exactly once, stop AI/navigation, cancel attack windows and disable damage/hurtbox participation. Keep a separate visual actor to show the hit reaction, loss of balance/fall or a deliberately authored disappearance, then hold the final pose and clean up. Remove it from the living-enemy count immediately; do not let delayed visuals attack, block clear conditions forever, or award loot again. Delay intrusive victory/reward overlays until the decisive motion is readable. A particle burst followed by immediate queue_free/array removal is not a death animation.

Use a non-looping AnimationPlayer/AnimationTree clip, AnimatedSprite2D sequence or authored cutout poses. Match cleanup to the actual animation completion including playback speed and transitions. Never wait for animation_finished on a looping clip, and do not globally disable the node's animation update when stopping AI. For pooled actors cancel old callbacks and reset all animation/material state before reuse. Save canonical dead/reward state independently of transient visual clocks, so restart cannot resurrect killed enemies or duplicate rewards. Scene exit may discard presentation safely. Use a bounded corpse/effect pool appropriate to the game and representative performance; this is not a generation-loop limit.

Write design/animation.md for the actual characters: visual source/rig, required clips, timing and transitions, contact/recovery/cancel windows, death/cleanup policy, and repeatable verification inputs. Idle/walk/attack/hit/death are a useful combat baseline, not a forced vocabulary for every game. Correct the most noticeable motion failures during /polish, especially instantaneous disappearance, floating feet, static weapons and sliding root motion.

## Choose a coherent asset pipeline

- 3D: reuse suitable authored skeletal clips, retarget to the character's rig, and refine in Blender. Bone mapping/rest pose, skin weights, grip, foot contact, root motion and transitions all need inspection. A rig makes motion possible; it does not provide actions by itself. Import clips into Godot AnimationLibrary and use AnimationTree for transitions/blending. Keep gameplay contact events aligned to visible motion. [Godot retargeting](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/retargeting_3d_skeletons.html), [AnimationTree](https://docs.godotengine.org/en/stable/tutorials/animation/animation_tree.html).
- 2D cutout: generate consistent separate body/limb/weapon artwork from one inspected character reference, place pivots at joints, then animate the parts in Godot or Blender. Add hand/face replacement drawings where deformation alone looks wrong. 2D does not require a 3D model. [Godot cutout workflow](https://docs.godotengine.org/en/stable/tutorials/animation/cutout_animation.html).
- 2D frame animation: first define the action, camera, direction, silhouette, grounded pivot and key poses (anticipation/contact/recovery or impact/fall/rest). Use world_generate_image with the SAME approved character reference and pose references for a consistent sheet or a few keyframes; do not independently regenerate every frame from text. Inspect identity, equipment, frame order, grid, alpha, scale and foot alignment. Generate/revise intermediate poses only where needed, preserving reference frames. Import validated frames with per-frame timing into SpriteFrames/AnimatedSprite2D. Avoid uniform timing by default; death must not loop. Generated grids and transparent backgrounds require inspection, not blind equal slicing. Check actual playback for flicker, duplicated frames and limb/weapon discontinuities. Image generation is an authoring step; never call it every playback frame.
- 2.5D or many directions: a single rigged Blender character and fixed orthographic camera can render coherent animation frames, then export a sprite sheet for Godot. Preserve action ranges, pivots, facing, frame durations and event timing in metadata. This shares the 3D animation workflow while using a 2D runtime.

## Source-checked reuse options

These are optional references, not bundled third-party assets or verified automatic adapters. Check the chosen release, license, engine compatibility and character fit before copying/installing.

- [Quaternius Universal Animation Library](https://quaternius.com/packs/universalanimationlibrary.html): CC0 humanoid motion assets including locomotion, combat and deaths, with Godot-oriented exports. The author offers free and paid tiers; do not assume the entire advertised library or Blender sources are in the free download. Prefer an appropriate existing clip over inventing motion entirely in code.
- [Blender Rigify](https://docs.blender.org/manual/en/latest/addons/rigify/index.html): build a usable control rig from aligned components, then skin/animate/bake and export. It is a rigging tool, not automatic polished gameplay motion. Confirm availability in the installed Blender version.
- [blender-spritesheets](https://github.com/theloneplant/blender-spritesheets): MIT addon/reference for rendering Blender actions into sheets plus metadata, with a Godot importer. Its README targets Blender 2.81; borrow the workflow or test compatibility before adding it to a current install.
- [Make-It-Animatable](https://github.com/jasongzy/Make-It-Animatable): research auto-rigging route for humanoid models; repository code is MIT while model weights/data have their own terms. Setup involves Python, pretrained files and external conversion tools. Treat as an optional experiment, not a turnkey macOS dependency. It does not replace gameplay clip selection or engine integration.
- [Sprite Sheet Diffusion paper](https://arxiv.org/abs/2412.03685): research into reference/pose-conditioned sprite sequences, useful for the temporal-consistency approach. This guide does not promise a tested OpenFun integration or redistribute its weights.

OpenFun already offers Meshy rigging and animation tasks for suitable textured humanoids. Search world_animation_library for real IDs; do not invent clip IDs. Actively use this path when suitable, configured and authorized; existing authorization need not be repeated for each required clip. Separate API billing is not a reason to substitute primitive motion. Respect explicit user limits, reuse good clips and use Blender for custom or non-humanoid actions. Blend/retarget and verify the downloaded GLB rather than treating successful generation as a finished character.

## Preserve material quality through rigging and animation

A real Meshy character test exposed a concrete failure: the textured source had base color, packed metallic/roughness and normal maps, while its rig/animation GLBs retained a diffuse map but introduced emission/specular settings and omitted the source PBR maps. Successful rigging therefore produced visibly glossy clothing and skin. Do not assume this occurs for every model or blindly disable intentional glow; compare the actual source and returned asset.

Keep the textured pre-rig GLB. For the same character, `openfun_mesh_materials.gd` (included in new projects) can restore its imported material per instance when UV triangle topology matches, allowing tiny Godot import precision differences. Call `restore_matching_materials(animated_actor, source_scene_instance)` once at load, inspect the restored/skipped counts and free the unused source instance. It preserves source textures/settings and does not overwrite shared imported resources. It deliberately skips ambiguous matches or changed UV charts; those require explicit Blender/material review. Never copy a material just because surface counts match. Inspect the before/after render under identical light.

The companion animation probe captures actual imported poses and normal-speed playback, reports action names/durations and bone motion, and can render a comparison using the original material source. Use real generated assets when authorized. Do not call correct bone motion a finished combat system: verify root-motion ownership, ground contact, weapon grip and actual damage timing in the game. For example, a tested hit clip moved the hips more than a meter; playing it on a stationary collision body would detach visuals from gameplay. Use collision-aware root motion or an intentionally authored in-place variant, then retest.

## Verify a sequence, not a still

Create a repeatable encounter. Read project inputs, then use world_preview_game inputs plus captureTimes around windup/contact/recovery. Key times are seconds from scene instantiation; account for loading. Inspect every returned frame. Add game-side logs/assertions for attack ID, target ID and hit time: screenshots alone cannot prove collision correctness.

Exercise miss, contact, held-button repeat, dodge/cancel, lethal hit, simultaneous lethal hits and restart. Capture pre-hit, impact, mid-fall, held final pose and cleanup. Assert the actor is visually present during its death motion but cannot attack/take damage, the final kill does not get hidden by an immediate modal, cleanup completes, and death/rewards are committed once. Test paused time, scene exit and pooled reuse where implemented. For imported 3D clips inspect normal-speed turns, foot/hand contacts and transitions; for sprites inspect a whole loop plus non-looping death, not a contact sheet alone. Assert no damage outside active frames, no duplicate damage per target per attack, and no invisible hit through a wall. Inspect normal playback too: a few keyframes cannot establish natural motion. Tune timing with actual play; do not prescribe a universal number of milliseconds for every weapon.

## Reuse

[GDQuest's Godot 4 hitbox/hurtbox demo](https://github.com/gdquest-demos/godot-4-hitbox-hurtbox) is a useful implementation reference. Its [license](https://github.com/gdquest-demos/godot-4-hitbox-hurtbox/blob/main/LICENSE) distinguishes MIT code from CC-BY-NC-SA 4.0 art. Do not treat its textures/models as unrestricted commercial game assets. Recheck the selected version before copying. [Godot demo projects](https://github.com/godotengine/godot-demo-projects) provide animation and input examples; use a branch matching the installed engine. No external demo code or assets are bundled by this guide.
